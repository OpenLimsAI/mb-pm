# 个人助手请求诊断

每次通过身份和输入校验的消息请求生成独立 `diagnostic_id`。同一问题重试保留客户端 `request_id`，每次尝试有不同诊断编号，方便区分失败与重试；成功请求在 `X-Assistant-Diagnostic-ID` 响应头中返回编号，服务端失败提示中直接显示。页面自身超时/断网时显示原请求 UUID，运维也可用该编号查询后台是否仍在处理或已保存。

这套日志用于查明失败原因。新后台请求同时采用独立的连接、读取和整轮生成时限；原同步接口保持兼容。后台任务不会因断网或重启自动重复调用模型。2026-11-04 的代码对已验证官方模型的输出超限及官方Kimi无可见正文的有界超时共用一次恢复额度，沿用原请求编号和总时限；认证、额度、限流和一般网络失败仍不自动重试。部署状态以发布回执为准。既有失败若未留下细节，无法事后恢复；需上线后复现。

## 能区分什么

| 类别 | 判定依据 |
|---|---|
| `model_timeout` | 连接、首响应、首正文、读取停滞、整轮时限或上游408/504；结合 `timeout_kind` 和 `transport_phase` 区分 |
| `output_limit` | 模型 `finish_reason` / Ollama `done_reason` 为 `length` |
| `response_too_large` | 接收字节数或本地正文容量达到上限 |
| `model_auth` / `model_rate_limit` | 上游明确返回 401/403 或 429；429 无法单凭状态区分额度不足与频率限制 |
| `model_network` | 网络、DNS、连接中断等非超时错误 |
| `model_invalid_response` / `model_empty_response` | 模型结果无法解析或未返回正文 |
| `query_timeout` / `query_limit` | 整轮知识查询的总时间/工具次数达到上限 |
| `dependency_*` | 知识库等依赖不可用；结合 `stage` 判断发生位置 |
| `unexpected_error` | 未预期的系统异常，保留编号供定位，不输出异常原文 |

每次尝试记录开始和结束、处理阶段、工具名及耗时、模型每轮耗时与时限、流式开关及推理等级、连接/发送/响应头/首数据/首思考活动/首正文阶段、超时类型和距最近数据的时间、首次可见正文时间（`model_first_content`）、输出额度（包含 `max_tokens`、`max_completion_tokens` 或 Ollama 对应额度）、结束原因、模型返回的 token 用量及 HTTP 状态。未提供的元数据保留为空，不推测超时或超限。查询参数、路径、论文标题、问题、正文、推理内容、回答、用户身份、端点 URL、密钥、原始异常和调用栈均不写入该诊断日志。

已识别的输出容量问题使用 422，模型或依赖暂不可用使用 503；不将这些业务失败作为 502/504 网关错误返回，避免入口代理替换错误正文和编号。原依赖状态在 `dependency_status` 中保留。真正的入口异常仍可能遮蔽响应，此时页面使用原请求 UUID 查询后台。

## 输出超限与有界恢复

`output_limit` 表示服务商明确结束于 `length`，不等同于等待超时。完成 tokens 可能全部用于思考而没有可见正文；应结合 `reasoning_tokens` 与 `completion_tokens` 判断，不能只按等待秒数猜测。

普通和知识库个人问答对已验证官方 DeepSeek 统一采用8192/低思考；用户明确要求深入分析或详细推导时采用16384/较高思考。恢复使用16384并关闭思考，沿用同一模型、端点和本轮授权证据，不执行输出被截断的工具参数，也不重新扩大工具次数。恢复是原后台请求内最多一次模型调用，受原 deadline、停止状态和工作令牌检查约束；不会因停止或租约失效而启动第二次调用。

输出超限恢复记录 `output_recovery_started`，Kimi空回答超时恢复记录 `timeout_recovery_started`；两者共用一次额度。随后新的 `model_started` / `model_completed` 仍属于同一次请求诊断，模型轮次继续递增。阶段 `recovering` 表示正在执行该恢复，正文开始后回到 `generating`。有该事件不代表最终恢复成功，仍须检查终态和错误分类；再次超限不会无限重试。认证、额度、限流、拒绝和网络失败保留实际分类，不改写成输出超限以触发恢复。

知识库非流式结果的草稿在可见正文清洗、来源路径及权限检查后才持久保存；推理内容和未验证的续写不作为草稿或完整回答。若恢复失败，只保留之前合法写入的安全正文。用户的“根据草稿重新整理”是另建请求、重新核对资料后生成完整回答，并非直接追加旧回答。人工操作与自动有界恢复应按请求编号区分。

## 运维查询

日志由专用 logger 写入容器标准输出，不新增公开查询接口。使用已有 SSH 运维权限查询；不把完整运行配置或凭据发给用户。

```sh
# 在持有源码的运维环境；文件路径按当前发布目录调整。
reader=releases/当前发布标签/scripts/read-assistant-diagnostics.py
docker logs --since 1h mb-pm-v2-app-1 2>&1 | python3 "$reader" --failures
docker logs --since 1h mb-pm-v2-app-1 2>&1 | python3 "$reader" --id '页面中的诊断编号或请求编号'
# 直连入口同样查询 mb-pm-v2-app-direct-1。
```

例如 `model_completed` 记录 `finish_reason=length`、随后 `request_failed.code=output_limit`，即确认回答达到输出上限；`model_failed.code=model_timeout` 则是模型等待/读取超时。两者不能仅靠耗时猜测。仅有页面等待超时不说明后台也超时，要用 request_id 核对后台事件。

## 保存与容量

生产两应用的 Docker json-file 日志各限制为每文件 10 MB、最多 5 个文件；不是按天保留，旧文件会轮转覆盖。重建容器也会移除旧容器日志。发布前须将现有诊断 JSONL 导出到权限 0600 的发布备份目录；主部署指南已补充命令。它不是永久日志归档，也没有新增数据库表、监控平台或自动告警。

本次按分类、隐私、重试、并发及前端编号显示做测试。生产部署及真实问题复现结果以独立发布记录为准；本地模拟测试不等于真实模型验收。

## Kimi阶段诊断与超时恢复

官方Kimi普通/联网整理采用 `low` 和16384完成tokens预算，明确深度分析用 `high`；知识库工具轮次保持非流式及来源检查。普通与联网最终回答流式返回，只记录思考活动的时间标记，不输出或保留思考文字。日志正确标记Kimi厂商，并保留 `stream`、`reasoning_effort`、安全枚举 `transport_phase`、`timeout_kind` 和有界计时字段；不以模型名称猜测未知代理的厂商。

阶段上限为连接/发送15秒、首响应150秒、首次可见正文180秒、读取空闲120秒，受同一默认300秒总预算限制。模型调用起点、收到响应头、首字节、首次思考活动与首段正文分别可定位，持续心跳不会无限延长无正文等待。上游408/504保留 `upstream_timeout`，业务响应仍采用503及原诊断编号。

仅官方Kimi无可见正文、原传输线程已退出、剩余至少60秒且任务围栏有效时，允许同模型简洁恢复一次，复用已经搜索的证据；输出超限与超时共用额度。已返回正文则保存草稿而不自动重放。验收应覆盖121秒首响应、持续思考无正文、正文后断流、剩余时限不足、取消/租约失效、同模型恢复及不重复搜索。
