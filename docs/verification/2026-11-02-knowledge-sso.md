# 知识库重复登录与报告资料视图恢复

## 已确认的故障链

2026-11-02 对生产环境进行了只读核对：四个 IAM 应用的 `enableSigninSession`、`enableAutoSignin` 均开启，`cookieExpireInHours=168`。没有发现这些单点登录开关被回退。

IAM 使用 Casdoor 文件会话：`redisEndpoint` 为空，进程工作目录为 `/`，会话目录为 `/tmp`。旧容器只持久化配置与品牌资源，没有持久化 `/tmp`。因此重建 IAM 容器会丢失提供跨应用单点登录的会话，而门户和知识库各自持久化的应用会话仍可存活，造成“工作台仍已登录，进入知识库却要再次登录”。这与官方 [v3.152.0 会话初始化代码](https://github.com/casdoor/casdoor/blob/v3.152.0/main.go#L35) 一致。

现场核对的 IAM 于 `2026-11-02 23:03:07 UTC`（纽约时间 18:03:07）重建。没有保留用户发生故障时的浏览器请求，因此不能断言每一次重复登录都由这次重建触发；未持久化会话本身是已确认的可复现缺陷。

### 本次具体触发事件的补核

生产发布回执 `security-hardening-20261102/iam-release-ca63f1f/iam.rollback.json` 写于 `23:03:06.910 UTC`，记录此次安全加固把 IAM 从镜像 `95c7be68…` 切换到 `bc7f85bb…`，源码为 `ca63f1f`。Docker 的 `Created=23:03:07.045 UTC`、`StartedAt=23:03:07.461 UTC` 证明是容器替换，而非仅进程重启。对应 `maibo-iam-release-fixed.py --apply` 已成功执行；脚本保留配置并检查 OIDC discovery，但没有迁移临时目录中的登录会话。

用户首次反馈所在聊天创建于纽约时间 `18:10:00`，在上述替换约 7 分钟后。因此本次最直接证据指向这次 IAM 安全升级触发旧会话丢失。此前仅更新业务应用、或不替换 IAM 容器时，不会触发这一存储缺陷。此处区分“发布确实清空旧 IAM 会话”的事实与“该用户每个请求的具体响应”尚未留存的边界，不把功能被删除或 SSO 开关回退当作原因。

知识库 `/data/mbweb/auth.sqlite` 已持久化，核对时有有效会话且含续期令牌，未发现无法解密的会话。没有证据支持把本次故障归因为知识库资料丢失、SSO 配置关闭、刷新令牌缺失或 IAM 禁止 iframe 的响应头。

报告端还存在独立的恢复缺陷：未建立或已失效的知识库会话在 iframe 内启动 OAuth，而报告仅等待 `ready` 消息；8 秒后以通用“资料视图暂未加载”提示遮住 iframe。认证、权限、服务错误未区分，也没有安全恢复入口。浏览器现场随后显示 280 篇论文，只能说明当前会话已恢复，不能证明旧缺陷已修复。

## 修复边界

- 持久化 IAM 文件会话；迁移时保留现有会话、权限及当前固定镜像，不改变账号、密码、角色或会话期限。
- 在知识库服务端门禁及运行期间识别嵌入页认证失效，通过固定事件协议通知报告；所有访问仍由原 OIDC 与知识库权限检查决定。
- 报告仅接受来自指定 iframe / 知识库源的消息，区分需同步登录、无权限与服务不可用。恢复在独立窗口完成，保留未保存正文，完成后重新加载资料。
- 不向前端传递服务令牌，不共享不同应用的 cookie，不通过扩大权限或延长登录期限解决问题。

代码测试、PR、固定合并提交及生产验证在对应发布记录中分别登记；本调查记录本身不代表已部署或完成真实账号验收。
