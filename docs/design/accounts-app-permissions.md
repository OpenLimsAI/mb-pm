# 账号管理应用权限改造方案

日期：2026-10-18。状态：方案已按 TDD 实现并完成本地验证；SVG 使用虚构账号，线上尚未发布。[验证记录](accounts-app-permissions-verification.md)包含测试范围、覆盖率和实现截图。

在门户 `/accounts` 的「编辑账号 → 资料与身份」中，分开维护平台管理身份与应用权限。保留现有四个编辑页签，将内容拆成公共资料、平台管理身份、项目管理、知识库四个区域。系统管理员独立于应用角色，知识库仅开放「可编辑」选择，「仅阅读」显示为禁用状态。沿用既有 IAM 角色，不批量修改已有账号的授权。

## 页面原型

- [编辑面板 SVG](accounts-app-permissions-edit.svg)：平台身份为普通成员，项目管理为项目负责人，知识库选中可编辑、仅阅读置灰，展示从历史阅读权限升级的待保存状态。
- [账号列表 SVG](accounts-app-permissions-list.svg)：平台身份、项目管理、知识库分别成列；系统管理员的 PM 权限标注为继承。
- [编辑面板 PNG 预览](accounts-app-permissions-edit.png)及[列表 PNG 预览](accounts-app-permissions-list.png)仅用于方便预览，SVG 为可编辑源文件。

## 页面设计

### 编辑面板

保留「资料与身份、用户名、重置密码、停用 / 删除」四个页签。桌面弹窗最大宽度建议从现有约 620px 扩为 900px，高度受视口约束，内容区独立滚动，标题、页签和操作栏固定。窄屏改为单列，选项不横向溢出。

1. **公共资料**：姓名、邮箱；标注为各应用共用资料。
2. **平台管理身份**：单独一块，选择普通成员或系统管理员。系统管理员可管理门户组织账号，且沿用 `admin` 对 PM 全部权限的覆盖；不自动获得 KB 编辑权限。
3. **项目管理**：独立应用卡片，包含员工、项目负责人两个可选业务角色，以及专业组、每周可用工时。工时沿用 0–80 整数规则。项目负责人适用于全部项目。目标为系统管理员时，角色区显示「继承系统管理员的全部权限」，业务角色只读保留，专业组与工时仍可维护。
4. **知识库**：展示仅阅读、可编辑两个选项，但「仅阅读」置灰、不可点击且标注「暂不开放」；只有「可编辑」可选，对应 KB 已有编辑能力。实际数据和操作权限由 KB 后端执行。
5. **保存栏**：汇总本次修改，例如「知识库：仅阅读 → 可编辑」，统一提交；无修改时禁用保存，提交失败保留草稿。角色修改后提示重新登录相应应用。

本轮不增加应用开通开关，也不提供「知识库管理员」。`dikw-admin` 属于另一个管理入口，不并入 KB 编辑权限。账号级停用继续放在「停用 / 删除」。

### 账号列表与新建账号

账号列表将原「身份」拆为「平台身份」与「项目管理」，并增加「知识库」列。系统管理员在平台列显示，PM 列显示「全部权限」及「继承」标识；普通成员显示实际 PM 业务角色。专业组、周工时、状态保持现有用途。项目负责人继续只读查看列表，系统管理员可编辑。

新建账号默认「普通成员 + PM 员工 + KB 可编辑」。系统管理员单独设置；KB 仅阅读置灰，不开放其他 KB 授权选项。

缺少 KB 角色时，列表显示「待分配」，编辑卡片无选中项；已有 `kb_viewer` 的账号保留当前只读状态，在禁用选项上显示「当前为历史阅读权限」。打开编辑面板、只改姓名或 PM 档案均不自动升级。管理员主动选择「可编辑」后才提交升级。原「知识库尚未开通 → 修复」改为「分配知识库编辑权限」，进入编辑面板的 KB 区域。

## 权限映射与兼容规则

| 应用 | 界面选项 | IAM 映射 | 边界 |
|---|---|---|---|
| 平台管理身份 | 普通成员 | 无 `admin` | 账号管理权限仍按 PM 负责人规则判断 |
| 平台管理身份 | 系统管理员 | `admin` | 门户账号管理写权限，PM 继承全部权限；不隐含 KB 编辑权限 |
| 项目管理 | 员工 | 沿用当前无显式管理角色时默认 `rd` 的规则 | 日常更新本人负责的任务；不能修改账号 |
| 项目管理 | 项目负责人 | `cmc_lead` | 重要编辑适用于全部项目；账号管理只读 |
| 知识库 | 仅阅读 | 历史 `kb_viewer` 只读展示 | 本轮禁用新增、切换和提交此选项 |
| 知识库 | 可编辑 | `kb_editor` | 以 KB 自身编辑权限校验为准 |

系统管理员属于平台管理身份，不作为 PM 的第三个业务角色。平台设置只管理 `admin`，PM 业务角色更新只管理 `ROLES - {admin}`，KB 更新只管理 `{kb_viewer, kb_editor}`。修改 PM 业务角色时不得移除系统管理员角色；修改平台身份时不得清理原 PM 业务角色或 KB 角色。

系统管理员的 PM 权限由 `admin` 覆盖，移除平台管理员身份后回落到保留的 PM 业务角色；没有显式业务角色时回落为员工。取消管理员的摘要必须说明该结果；仍禁止取消自己的系统管理员身份。

旧 `project_lead` 显示补充标识「本人项目」，旧 `production`、`qa_qc` 显示实际角色说明。只改资料、KB 权限或保持 PM 角色不变时，保留原始 PM 角色，避免把 `project_lead` 无意升级为全部项目负责人。仅在主动变更 PM 身份时按现有规则归一化，并在提交摘要中说明范围变化。

同时持有两个 KB 角色时按编辑者显示；未主动修改 KB 权限则保留原始成员关系，主动选择可编辑后才归一为 `kb_editor`。`viewer` 与 `unassigned` 只用于响应和展示，均不是可提交的授权值。未分配状态不等同于已验证的拒绝访问。

这里的系统管理员 `admin` 不等同于 Casdoor 组织管理员属性 `isAdmin`，后者继续按现有规则只读显示并保留敏感操作限制。系统管理员也不等同于 `dikw-admin`。本轮将平台身份从应用角色的设置中分离，但保留平台管理员对 PM 全部权限的覆盖；若以后需要「只能管理账号、不能查看项目」的管理员，须另设角色与授权边界。

## 接口与保存逻辑

复用 `GET /api/v1/portal/accounts`、`POST /api/v1/portal/accounts`、`PATCH /api/v1/portal/accounts/{id}`，不增加页面路由。

- 读写字段新增 `platform_admin: boolean`，只管理平台 `admin` 角色。
- 读写字段新增 `pm_identity: lead | staff`，只管理 PM 业务角色；响应新增只读 `pm_effective_role`，供管理员的继承权限及历史角色展示。
- 写入字段新增 `kb_role: editor`，服务端枚举只接受 `editor`；响应允许 `viewer | editor | unassigned`，兼容历史角色和待分配状态。请求提交 `viewer` 必须在写入前返回校验错误，不能只依靠前端置灰。
- 旧 `identity` 可暂时保留为只读兼容字段；新版写接口拒绝旧 `identity` 请求并提示改用拆分字段，避免旧整包请求误覆盖平台身份。
- 响应新增只读 `kb_roles: string[]`，保留 `pm_roles`、`other_roles` 与过渡字段 `kb_enabled`。`kb_enabled` 继续表示显式 KB 角色准入，最终数据权限由 KB 自身检查。
- PATCH 只处理显式提供的字段；不把字段省略或 `null` 解释为回收角色。不接收浏览器提交的任意角色数组或其他应用角色。

修改知识库权限的请求只需：

```json
{
  "kb_role": "editor"
}
```

保存流程：

1. 沿用每次请求实时核对操作人、限定组织、验证门户 Origin、自身管理员保护及临时密码检查。
2. 读取最新目标账号和角色；校验请求枚举与待添加角色确实存在且启用。在任何写入前完成检查。
3. 分别计算平台、PM 与 KB 的角色差异。平台字段只改 `admin`；PM 字段不触碰 `admin` 或 KB 角色；KB 字段只允许归一为 `kb_editor`，其他角色原样保留。
4. KB 单独修改不调用 `_ensure_member`，不为尚未进入 PM 的账号创建项目管理档案。公共资料只同步已有档案；主动修改 PM 档案时才关联或创建成员。
5. 写 IAM、同步必要的本地档案、写审计，再回读 IAM 确认真实结果。审计分别记录平台身份、PM 角色、KB 角色的前后值及差异，不记录密码。
6. 当前 IAM 写入与数据库提交不构成跨系统事务。实施时补充失败补偿与回读：记录已成功步骤，失败后核对并补偿本次变更；补偿失败明确报错和记录修复事项，不返回虚假的全量成功。

Casdoor 当前按整条角色记录更新成员列表；同时编辑不同账号也可能操作同一个角色。实现时对本服务的角色读改写使用跨进程共享的串行机制，并回读校验；IAM 管理台不受本服务锁控制，有条件更新能力时应优先使用，外部并发冲突须检测并提示刷新。

现有 `repair` 混合处理密码、PM 成员和 KB 开通。改造后将 KB 分配移到显式编辑流程；处理其他问题不得顺带赋予 KB 编辑权限。缺角色提示应说明待配置的 IAM 角色，不能自动退回权限更高的选项。

## 生效时机与知识库联动

先按现有机制设计为「IAM 保存后，重新登录相应应用采用新角色」。列表从 IAM 回读显示保存结果；门户 `/portal/me` 的应用目录需刷新最新 KB 角色，避免继续展示旧令牌里的准入状态。不要把仅隐藏入口当作撤权完成。

KB 独立维护会话，mb-pm 现有 `end_sessions` 无法清除 KB 会话；清理门户 / PM 会话也不能吊销已签发的 Bearer JWT。必须分别验证：历史阅读者保持只读、明确升级为编辑者后新登录获得写权限、只修改其他资料不升级权限，以及退出后通过 SSO 重新登录是否取得新角色。本轮不提供 KB 降为阅读者的操作。

取消平台管理员或降低 PM 业务角色时，若要求立即生效，应把旧会话与旧令牌的处理列为发布前置。KB 的实际角色映射、编辑授权生效时机及受保护写接口需在当前运行版本验收，不复用历史候选补丁的通过结论。

## 验收清单

- 平台身份与 PM、KB 分区显示，系统管理员不出现在 PM 可选业务角色中；PM 员工、负责人均可搭配 KB 编辑者。
- 系统管理员的 PM 权限标注继承；修改 PM 不移除 `admin`，取消其他人的管理员身份按已保留的业务角色回落；KB 不因平台身份变更而改变。
- KB 仅阅读置灰且不可键盘选中，服务端拒绝 `viewer` 写入；历史阅读者只改资料不会被自动升级，明确选中可编辑后才授权。
- 只改 KB 的账号不新增 PM 成员；只改姓名不修改角色；旧 `project_lead` 的本人项目范围、`production` 和 `qa_qc` 原角色保留。
- 知识库待分配、同时持有两个 KB 角色、角色不存在或停用、旧身份写入、参数非法均有确定结果。
- 项目负责人不能写接口；管理员不能取消自身管理员身份；原有组织管理员、账号停用、重置密码、删除保护保持有效。
- IAM 写入中途失败、数据库提交失败、两个管理员并发编辑不被误报成功，回读结果与审计可核对。
- 新建账号的两类权限按选择分配；任何非 KB 的修复不会补发 `kb_editor`。
- 真实历史 KB 阅读者受保护的写接口返回 403；编辑授权、新旧会话、门户目录、SSO 重新登录分别记录验收结果。
- 桌面与窄屏可完整查看两张应用卡片；键盘可操作角色单选；无修改不保存，失败不丢草稿，关闭未保存内容时有提示。

验证命令、模块覆盖范围和门槛见 [本地开发与测试](../development.md#构建与测试)。前端使用组件与 HTTP 边界集成测试，后端通过公开 API、真实数据库和外部 IAM 替身测试，不连接生产 IAM。

## TDD 开发记录

每个核心行为先补失败测试，再实现并复跑通过；随后补充存量操作的回归覆盖。

| 行为 | 初始失败表现 | 完成后的行为 |
|---|---|---|
| 独立读取平台身份 | 账号响应缺少 `platform_admin` | 平台身份、业务角色、有效角色及 KB 角色分别返回 |
| 单独设置管理员 | PATCH 被忽略但返回成功 | 管理员切换保留 PM 与 KB 原角色 |
| 修改 PM 业务角色 | 未更新 `pm_identity` | 只变更业务角色，不移除 `admin` |
| KB 只读禁用 | 接口忽略 `viewer` 并返回成功 | UI 禁用，后端校验拒绝 |
| KB 明确升级 | 角色不变且意外创建 PM 成员 | 仅更改 KB，PM 档案保持未创建 |
| 新建字段拆分 | 仍提交或读取旧的单一身份 | 前后端使用三个独立权限字段 |
| 修复不赋权 | 修复成员同时补发 KB 编辑权限 | KB 分配改由显式编辑完成 |
| 写入失败与回读 | 部分角色、姓名已变更；IAM 无效写入被误报成功 | 对本次写入回读并补偿，补偿失败明确报错 |
| 并发角色保存 | 两个请求互相覆盖成员关系 | 共享数据库锁串行保存，两个账号均保留 |
| 草稿离开提示 | 关闭即丢失修改 | 关闭或切换前可继续编辑或明确放弃 |
| 旧写入格式拒绝 | 旧 `identity` / 任意角色被忽略 | 返回 422，不改变授权 |
