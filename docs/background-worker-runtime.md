# 后台任务独立运行

后台任务独立运行时，网页和 API 仍使用同一应用镜像。网页进程提交任务并读取进度，后台进程从同一个 PostgreSQL 数据库领取任务。项目分析、个人助手异步生成、知识源处理、旧信息采集和笔记同步沿用各自的启用开关、领取规则和任务状态。

| `APP_PROCESS_ROLE` | 入口 | 用途 |
| --- | --- | --- |
| `combined`（默认） | `app.main:app` | 在应用进程中提供网页、API 和后台任务 |
| `web` | `app.main:app` | 提供网页和 API，由独立后台进程领取已排队的任务 |
| `worker` | `app.worker:app` | 运行启用的后台队列，使用容器回环地址提供健康检查 |

个人助手的旧同步消息接口仍按原方式等待回答。当前浏览器使用的异步请求与项目分析任务通过数据库队列执行。独立后台进程要求 `AUTO_MIGRATE_SCHEMA=false` 和 `AUTO_SEED=false`，数据库结构升级仍使用单独的维护身份。

## 启用独立后台进程

先在隔离环境用同一版本的应用镜像和合成数据验证网页提交、后台领取、结果回读和重启后的状态。生产切换使用当前运行容器记录的完整 Compose 文件顺序和环境配置。启用前确认现有应用使用已包含独立入口的固定镜像，生产硬化配置已生效，并更新服务器上的停写备份与运行监控脚本。

在服务器上用完整的现行 Compose 命令生成附加配置。下例中的 `production_compose` 代表已核对的命令，包含项目名、目录、环境文件及全部 `-f` 参数。生成文件包含运行凭据，放在服务器私有目录，权限为 `0600`，与备份范围内的其他生产配置一起管理。

```sh
production_compose config --format json |
  python3 deploy/parallel-test/worker_overlay.py --output "$worker_overlay"
production_compose -f "$worker_overlay" config --quiet
production_compose -f "$worker_overlay" up -d --no-deps --wait --wait-timeout 120 worker
production_compose -f "$worker_overlay" up -d --no-deps --wait --wait-timeout 120 app app-direct
```

若当前部署只包含 `app`，最后一条命令仅指定 `app`。通过追加配置将网页实例切换为 `web` 后，检查网页及维护入口健康，并验证一条新的排队请求能得到结果。之后的发布继续按同一文件顺序更新网页和后台进程，保持镜像版本一致。数据库凭据、模型配置、知识库网络或持久卷变更时，同步核对后台配置。切换安排在维护窗口，避开备份停写和其他发布操作。

## 健康检查、恢复和回退

独立进程只在容器内监听 `127.0.0.1:8001`。`/health` 检查各已启用队列线程是否存活以及数据库是否可连通。服务健康后，仍用实际的排队任务验证模型、身份服务及知识库连接。服务端监控在网页运行于 `web` 角色时要求后台服务存在并健康。更新备份和监控脚本后，停写备份会同时停止已存在的后台容器，并去重归档共享卷。

停机时会向各队列同时发出停止信号，独立后台进程最多等待 20 秒让执行线程退出。排队任务继续存放在数据库。等待超时或已开始的生成任务按现有超时、租约和中断逻辑结算，可能显示中断并由用户决定是否重试。

回退时，用启用前的完整配置重新启动 `app` 和现有的 `app-direct`，恢复默认组合角色。确认应用已重新领取后台任务后，用带独立配置的 Compose 命令停止并移除 `worker`。保留私有配置及数据卷用于核对。
