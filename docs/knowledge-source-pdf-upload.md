# 知识源 PDF 上传故障分析与修复

## 问题与复现

2026-11-16 收到生产 `www.openlims.ai` 上传约 1.2 MB 的 `Kimi-Linear-2510.26692v2.pdf` 失败截图。提示“已完成 0 份，其余文件可重试。暂时无法连接知识源”，该提示只能证明前端未取得成功回执，不能证明原件一定没有保存。

生产只读检查：门户 `c222145`、知识库 `deb5ab09` 均健康；桥接地址和签名配置存在，pypdf 6.21.4。临时目录可写且空闲 128 MiB；原件盘空闲约 38.5 GiB，配额 5 GiB，已使用约 114.6 MiB。应用回环入口对 4 KB 和 1.2 MB 的匿名 multipart 请求均返回 401，未发现应用 1 MB 限制。公网脚本被浏览器签名规则拒绝，不能把该探测当成用户失败原因。

从公开 arXiv 下载同名 v2：1,354,769 字节，SHA-256 `e2e23a449fc9bb27e34e783d20b2e6cd0f1ac67d58efdc0479c03c54db956a17`。实际解析约 3.8 秒，得到 94,051 字符，其中 40 个 U+0000（NUL）。知识库上传协议明确拒绝 NUL；PostgreSQL text 也不允许此字符。这是已确认、可重复触发的上传兼容性缺陷，与文件未超过大小上限无关。

## 修复

- 在 PDF 提取边界仅去除 NUL，保留其他正文字符、换行、制表符与原 PDF 字节；不绕过知识库输入校验。原件仍按原 SHA 保存。
- 不改变上传权限、25 MiB 限制、10 份批次上限和显式索引规则；上传仍 `parse=false`，不自动发起付费模型或全库索引。
- 对没有安全 JSON detail 的 413、500、502/503、504、请求超时分别提示；不把 HTML/堆栈直接显示给用户。
- 批次失败显示“已确认成功 N 份；当前文件保存结果未确认”，保留失败文件、已成功回执及撤销凭证。有部分成功时仍刷新列表一次。
- 上传时展示当前文件名、第几份/批次总数、已确认保存份数和浏览器报告的网络上传百分比。网络传输完成后显示“正在解析并保存”，不把网络 100% 当作保存成功；服务器返回成功回执后才确认完成。浏览器未报告总量时显示不定进度，不估算后端解析或保存百分比。

## 验证与限制

- 两种真实合成 PDF：字面 NUL 与字体 ToUnicode 的 NUL 映射；修复前失败，修复后清除 NUL 且原件 SHA 不变。
- 真实 multipart 路由贯穿解析、知识库输入契约替身、归档和正文持久化，并验证重复上传返回同一资料。
- 同名公开 PDF 修后 94,011 字符、0 NUL，结果严格等于原提取结果仅移除 NUL，其他控制字符和原 PDF SHA 不变。
- 前端覆盖两文件部分失败、首份超时、保留回执与失败队列、刷新一次，以及 HTTP/超时错误提示。
- 进度回归覆盖上传 25%、传输 100% 后等待回执、成功确认、下一份重新计量、未知总量、失败后保留资料、迟到回调和离开页面时取消当前请求。取消浏览器等待不代表已停止服务器处理，保存结果仍以回执和资料列表为准。
- 目前尚无用户截图对应时刻的浏览器 Network 回执或生产异常栈，因此不能声称 NUL 已解释截图中所有“连接失败”情况。KB 对 NUL 的正常拒绝应为 400 JSON detail；截图中的通用文案仍可能含另一层错误，修复后须再次核对真实上传结果。
- 修复及进度展示已于 2026-11-16 部署到生产，固定运行版本为 `7cd5ddcba44a7282bd130522e4a84dbea720cac6`。双实例与公开入口验证通过，实际用户文件上传尚待用户重试确认；详见 [发布记录](../deploy/parallel-test/releases/20261116-knowledge-source-pdf-upload.md)。
